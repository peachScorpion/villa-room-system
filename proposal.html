方案概述

OVERVIEW

1.1 项目背景

客户是一家举办大型激励/表彰类展会（含获奖人员、销售精英、团队（全董））的企业。活动期间需将参会人员分配入住别墅 A（7 栋）与别墅 B（2 栋），涉及双床房、大床房、浴缸大床房等多种房型与单人付费升级。

当前分房依赖 Excel 手工排房，痛点明显：分配状态靠人工标记、单人升级费用靠人算、跨团队拼房靠口头协调、错误率高且无法实时同步。客户已用 PPT 完整梳理出期望的流程与交互框架，希望落成一套可操作的智能分房系统。

1.2 产品定位

一句话定义：「别墅智能分房系统」是面向会务运营/团队负责人的 B 端效率工具，把「报名→分房→计费→校验→报表」全流程数字化，用拖拽替代手工排表。

平台端会务运营后台

数据导入、别墅资源管理、全局分房监控、报表导出

B 端团队分房工作台

以「全董」为单位的拖拽排房、升级计费、提交

结算付费升级闭环

单人升级 3200 元/间/全程的汇总、付款与标记回写

1.3 业务场景（用户故事）

每个场景用客户/使用者原话代入，覆盖三个核心角色。

平台端 · 会务运营
「我把报名表丢进去，就能按每个全董看到还有谁没排、哪栋别墅没住满。」

作为会务运营，我希望导入报名 Excel 后系统自动按「全董」（表单 M 列）分组、并按性别（D 列）计数，以便一眼掌握每个团队的分房进度与剩余床位。核心旅程：导入表单→自动分组计数→查看进度/空房

B 端 · 团队负责人/全董
「我拖一个人进房间，他就从待分配名单消失，房间床位实时更新。」

作为全董，我希望通过拖拽把团队成员安排进指定别墅房间，房间状态从 0/2 → 1/2 → 2/2 自动流转，以便快速完成分房并随时重排。涉及模块：拖拽排房、重排房间、升级单人入住。

结算 · 财务/收费
「谁升级了单人房、该收多少钱，系统自动算好，我直接出账单。」

作为财务人员，我希望系统对「付费升级单人入住」按 3200 元/间/全程自动计数汇总，回写 H 列标记，以便一键收款与对账。涉及模块：升级计费、付款、报表导出。

1.4 核心问题与解决思路

核心问题根因解决思路
分房靠手工、易出错Excel 表格 + 人工标记，状态不同步拖拽排房 + 房间状态（0/2、1/1、1/2、2/2）自动流转
进度不透明各团队分房数据割裂按「全董」分组，实时展示已分/未分、占床数量、剩余床位
升级费用算不准单人升级靠人工计数计费升级操作自动计数，金额=数量×3200 元，回写 H 列
奖励/房型约束漏安排获奖人员需住浴缸大床等规则散落获奖标签强提示 + 单人入住标记（G 列 Y）锁死升级按钮
拼房协调困难跨团队拼别墅靠口头/线下「拼别墅人数」可视化，会务组统筹兜底

1.5 方案要点

① 三栏式分房工作台

左=分房进度，中=别墅明细，右=待分配名单，一屏完成排房

② 拖拽 + 状态机驱动

房间状态自动计算，满房蓝块/未满橘块，一眼可辨

③ 计费闭环

升级→计数→汇总→付款，3200 元/间/全程自动累计

④ Excel 双通道

表单列映射导入 + 报表标准导出，无缝衔接现有流程

⑤ 规则校验兜底

提交前验证「待分配=0 且空别墅≤1」，拦截漏排/空房

⑥ 预留复用架构

按「活动」维度设计，为多场复用 SaaS 化留空间

1.6 总体架构

层次职责包含模块
触达层多角色 UI 入口会务运营后台、团队分房工作台、付费引导页
业务逻辑层核心规则引擎分房引擎、状态机、升级计费、校验规则
数据层结构化存储人员、别墅/房间、分配关系、升级标记、活动
集成层外部对接Excel 导入导出、支付、报表
一句话总结：把客户已想清楚的「手工排房流程」数字化，用拖拽 + 状态机 + 自动计费，把一次活动的分房从「数天排表」压缩到「数小时提交」，并为多场复用的 SaaS 化预留架构。

2.1 报名数据导入模块

  • 按活动导入报名 Excel，解析已有字段映射：C 列姓名 / D 列性别 / M 列全董 / K 列上手董事 / L 列上手区董 / G 列单人入住标记 / H 列付费升级标记。
  • 导入后按「全董」分组，计算该全董下报名人数、男女性别分类计数。
  • 提供导入校验：必填缺失、列错位、重复报名号时给出报错提示，避免脏数据进入排房。
待确认：Excel 版本与列固定规则、报名号是否唯一键

2.2 别墅资源管理模块

  • 维护别墅 A（7 栋）与别墅 B（2 栋），房型分别为：A=1-双床 / 2-双床 / 3-浴缸大床；B=1-双床 / 2-大床 / 3-浴缸大床。
  • 支持「活动组提前预分配别墅数量」，当总床位需求 > 原预分配床位总量时，可新增 1 间别墅 B 参与分配。
  • 展示每间房的分配状态：0/2 未分配、1/1 单人入住、1/2 未住满、2/2 已排满；满房蓝块、未满橘块。

2.3 分房工作台（核心交互）

采用三栏布局，一屏完成排房：

  • 左侧 · 分房进度栏：展示该全董下「已分房人数/总人数」、未排满别墅的已安排人数、剩余待排床位数。
  • 中间 · 别墅明细栏：别墅号（系统自动生成：别墅类型-全董编号-别墅号）+ 各房间床位状态色块。
  • 右侧 · 待分配名单栏：显示待分配人员卡片，含报名号、姓名、性别、同住意愿、是否愿拼大床、上手董事/区董、单人入住/获奖标签；男女用不同底色框。

剩余待排床位数计算公式：M 列计数 + G 列 Y 计数 + H 列付费升级单人入住数 − 已排人数。

2.4 拖拽排房与重排模块

  • 拖动名单中的名字至目标房间，名字落入房间并显示，右侧名单同步移除。
  • 每个房间提供「重排房间」按钮：点击后该房间所有已分配人员返回右侧名单。
  • 房间状态随操作自动更新，满房/未满颜色实时刷新。

2.5 升级计费模块（含获奖约束）

场景规则费用
付费升级单人入住弹窗确认后计入单人入住，房间置为 1/1，回写 H 列 Y3200 元/间/全程
免费单人入住（G 列 Y）如「至臻区董已付」「获奖人员单人入住」，升级按钮置灰不可用0
获奖人员需入住浴缸大床房，卡片展示「获奖提示」标签—
取消升级再次弹窗确认，取消后房间恢复可拼状态费用退回
待确认：获奖人员的「浴缸大床」是硬约束还是软约束？浴缸大床不足时如何降级

2.6 搜索/筛选/排序模块

  • 搜索：通过姓名 / 上手区董 / 上手董事进行搜索。
  • 筛选：按姓名、SE、RSE、性别做模糊查找。
  • 排序：顺位排序，主要关键字 RSE、次要关键字 SE。
待确认：SE / RSE 的准确定义与层级含义（推测为销售精英/区域销售精英）

2.7 校验与提交模块

  • 提交条件：每个账号待分配人数 = 0，且未排满别墅数量 ≤ 1。
  • 待分配人数 > 0 → 提示「还有人员未分配别墅，请分配好后再提交」。
  • 未排满别墅数量 > 1 → 提示「您有多套别墅出现空房，请分配好后再提交」。

2.8 付款模块

  • 有勾选升级单人入住的，按数量 × 3200 元/间/全程计总后跳转付款。
  • 付款成功后回写标记，生成可对账单据。
待确认：收款渠道（微信/支付宝/线下对账）、退款与开票流程

2.9 报表导出模块

按标准字段导出，覆盖：报名号、全董姓名、实际出行人、性别、同住意愿、愿意双人大床、单人入住、全董付费升级、别墅号、房间号、上手董事、上手区董、获奖/特殊说明、备注。

待确认：报表格式（Excel/PDF）、「备注/特殊说明」字段来源

2.10 权限与协同模块

  • 角色分层：会务组（全局）、全董/团队负责人（本团队数据范围）。
  • 跨团队拼别墅人数可视化，会务组统筹兜底。
重点风险：PPT 未定义多人并发——若多个会务组同时编辑同一「全董」分组，会出现覆盖冲突，需明确锁定/冲突提示机制。

难易程度评估

DIFFICULTY ASSESSMENT
总体判断：本项目整体不难，真正的难点只有 3 处，且都不在「技术实现」本身，而在业务规则与边界。只要守住「手动拖拽 + 单人单机 + 线下对账」这条边界，就是 2~3 周可交付的普通 B 端工具；一旦加入并发、自动排房、线上支付任何一项，难度与报价都会往上跳一档。

模块难度三档

难度涉及模块原因
简单分房进度看板、别墅明细/详情、报表导出、验证提交、房型配置标准「查数据 + 展示」，字段已定、无算法，纯增删改查
中等报名数据导入、待分配名单（搜索/筛选）、拖拽排房、单人升级计费需打磨交互与容错：拖拽手感、列表实时同步、导入容错、升级免费/付费/取消分支

三个真难点（决定工期与报价）

1
多人并发协同

若多个会务组同时编辑同一「全董」分组，涉及实时同步、占用锁、冲突提示，是架构级问题，工作量可能翻倍；若「一人排完另一人再排」则完全不构成难点。

2
自动排房算法

本项目的难度分叉点：客户 PPT 已是「手动拖人进房」，技术简单、难在拖拽体验；若实际要「系统按获奖住浴缸大床 / 男女不混住 / 同住配对 / 尽量装满」一键自动分配，则升级为约束求解问题（相当于排课/排班系统），难度与工期指数级上升。

3
线上支付对接

3200 元/间若走微信/支付宝线上支付，涉及支付回调、退款、对账，中等偏难；若仅「先算金额、线下来回收款」，则基本无需开发。

一句话：「好做」的边界很清楚——手动拖拽 + 单人单机 + 线下对账；任一升级为「自动排房 / 多人协同 / 线上支付」，难度与报价上跳一档，须回到待确认清单重新评估。

待确认清单

CONFIRM LIST

以下是影响架构与报价的关键空白点，立项前需与客户逐条对齐。前 4 条为「硬点」，直接决定技术方案与工期报价。

1
多人协同与并发（最优先）

多个会务组是否同时操作同一「全董」分组？是否需要实时协作、锁定/冲突提示？这决定是「单人单机工具」还是「多人协同系统」。

2
Excel 数据规范

报名表单的列是否可固定？报名号是否唯一？是否需要导入前的格式模板与校验规则。

3
动态新增别墅 B 的规则

「总床位需求 > 预分配床位」时新增 1 间别墅 B，谁来触发？是否需审批？是否可多次新增？

4
付款方式

3200 元收款走线上支付（微信/支付宝）还是线下对账？是否需要退款、开票、支付回调闭环。

5
获奖人员房型约束

「获奖需入住浴缸大床」是硬约束还是软约束？浴缸大床不足时的降级与提示逻辑。

6
男女/同住约束

「同住意愿」「愿意拼大床」是否参与自动排房，还是仅作参考、纯手动拖拽？男女生底色是否用于校验混住冲突。

7
系统复用性

是一次性活动交付，还是多场复用的 SaaS 工具？影响是否有「活动」维度、账号体系、历史数据留存。

8
权限边界

全董能否自助操作自己的分房，还是仅会务组代操作？不同全董之间的数据是否隔离。

9
术语确认

「全董」「上手董事/上手区董」「TOP SE / TOP RSE」等内部称谓的精确定义与层级关系，避免理解偏差。
